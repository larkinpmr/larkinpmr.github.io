# Larkin South Miami PM&R Hub — notes for Claude

Static site served by GitHub Pages at https://larkinpmr.github.io (repo `larkinpmr/larkinpmr.github.io`, branch `main`, root).

- `index.html` — the whole site (HTML, CSS, JS in one file). Design changes happen here.
- `data/snapshot.json` — the saved copy shown instantly before Google answers. **It is PUBLIC (GitHub Pages serves it to anyone)**, so it holds only non-personal content: academic year, the rotation list (names, codes, groups; no guide text), note templates and the readiness note. Never put residents, schedules, didactics, contacts, links, guide or policy text in it: `tools/trim_snapshot.py` enforces this and `tools/build_snapshot.py` / `tools/build_schedules.py` call it before writing. Signed-in devices cache the live data locally; pages show "Loading … from Google Drive" until it arrives (note templates and the readiness note live only here).
- `data/config.json` — `liveDataUrl` (public Apps Script web app, returns schedules/contacts; `?part=handbook` returns the Handbook; `?calendar=didactics` returns the .ics feed) and `adminUrl` (chief-only editor deployment, `?page=admin`); `signIn: "email"` makes a brand-new device show the email sign-in form immediately instead of a loading cover while Google wakes up — it removes itself if Google says sign-in is off, but drop the key if email sign-in is ever turned off for good).
- `apply/index.html` — public applicant page (interview season); reads only the Control Panel's "Applicant Page" tab via `liveDataUrl?part=apply`, falls back to `data/apply.json`. Never load resident data there.
- `assets/` — site icons; `assets/hb/` — Handbook pictures for the saved copy; `assets/files/` — lecture PDFs linked from the Handbook.
- `apps-script/` — copy of the Google Apps Script (Code.gs + Admin.html) that lives in the "Hub Control Panel" Google Sheet in the chief account. Editing these files here does NOT change the live script; the chief must paste them into Apps Script and create a new version of BOTH deployments.

Live content comes from Google: Didactic Schedule sheet, Resident Schedule sheet, the Handbooks Drive folder (one Google Doc per rotation/policy page; folder = category, Policies folder = Resources, doc name matches the Rotations-tab name; older setup: one Handbook doc split by Heading 1), and Control Panel tabs (Settings, Contacts, Quick Links, Announcements, Rotations, Page Edits). Never hard-code schedule or contact data into index.html.

Before pushing a change: keep both light and dark themes and phone width (~390px) working, and test with a headless browser.

Whenever a change alters how the chiefs run or edit the hub (new feature, new tab, new Settings row, new Apps Script function), also update `HOWTO_LINES` in `apps-script/Code.gs` (the Control Panel's "How to update" tab rewrites itself from it within ~5 minutes of the new code being pasted) and `HANDOFF.md`. Never tell the chiefs to type in the "How to update" tab.

**Standing rule from the chief (do not wait to be asked):** every time a new `Code (copy this).txt` is handed over, `HOWTO_LINES` in that same code must already describe everything the chiefs need for ALL changes since the last hand-over — script features, new or renamed Settings rows, tabs and columns (including Control Panel tabs the website reads, like Quick Links), one-time setup steps (Services, install functions), troubleshooting, and new-academic-year steps — plus website changes that affect what chiefs edit. Before delivering code: re-read the whole `HOWTO_LINES` list against the session's changes and fix anything missing or outdated, then update `HANDOFF.md` (and upload it to the Project as `claude/chief-handoff-guide.md`). A website-only change that alters what chiefs edit also needs `HOWTO_LINES` updated and a fresh code hand-over.
